# mxui dogfood QA report — 2026-10-09

Scope: web client (login, composer, components, modals, slash commands), gateway
API surface, event-injection security. Method: live browser session + direct
event injection + API probes. Gates green throughout (build/vet/test).

## Executive summary

**14 checks run, 3 findings (1 Medium design gap, 2 Low), 0 Critical.** The
client survived every hostile input without script execution or crashes; the
gateway rejected all unauthenticated/malformed API calls correctly.

## Findings

### 1. [Medium · Design] Resolved cards can be re-resolved by a different user
Dedupe is keyed per (message, component, **user**) — by design. Verified live:
user2 (@mxui-clicker2) clicked Approve on a card user1 had already approved;
the gateway validated it as fresh and forwarded the interaction (Discord-shaped
webhook received, confirmed on a live listener). Discord prevents this by
disabling components for everyone after the first interaction. Client-side we
only disable buttons when resolve-text appears. **Fix options:** gateway-level
per-message resolution state, or document as "bots must handle re-resolution
idempotently" for v1. Needs a decision.

### 2. [Medium · Security-adjacent] Actions on messages with no known component_message pass validation
The gateway's expiry lookup defaults `notStale=true` when it never saw the
paired `io.mxui.component_message` (e.g. after gateway restart with in-memory
state, or fabricated messageEvent ids). A fresh-timestamped action on an
unknown/fabricated message is forwarded to bots. **Fix:** default-deny when no
component_message is known for the target (requires persisting the pairing in
SQLite, which exists).

### 3. [Low · Robustness] Unknown component types and empty selects render silently
Injected a component_message with `type: "hologram"` and an option-less select:
rendered as a labeled button and an empty select; no crash, no console error.
Acceptable for v1 (forward-compat behavior) but an empty select is a dead
control — worth a "no options → render nothing" guard.

### 4. [Low · Logging] Gateway silent on successful forwards
Successful interaction forwards produce no log line (only REJECTED and webhook
failures log). Cost me 20 minutes today concluding the sync loop was wedged
when it was fine. One INFO line per accepted interaction would fix operability.

## Checks that passed

- Wrong password → clean error, stays on login ✓
- XSS: composer HTML/script payloads render as text, nothing executes ✓
- XSS: modal field values echoed as text, no execution ✓
- Rapid triple-click on Approve → single resolution (per-user dedupe) ✓
- Enter-key composer submit ✓; 5k-char text ✓; unicode/emoji/RTL ✓
- Forged actions (future ts, expired ts) → REJECTED by demo-bot and gateway ✓
- Gateway auth: bad token 401, no auth 401, garbage registration 400, missing
  webhookUrl 400 ✓
- Modal open/cancel round trip; card stays active after cancel ✓
- Page reload + re-login → full history re-render incl. paired components ✓
- Multi-user: second user joins room, interactions flow to webhooks ✓
- Scroll behavior, live sync, message edits ✓

## Not tested

E2EE rooms (v0.6 territory), federation (disabled on this homeserver),
concurrent same-millisecond duplicate event ids, mobile viewport rendering.
